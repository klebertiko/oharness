## Achados

### P2-1 — Denylist de leitura automática não cobre formatos de credencial conhecidos

**Local:** `backend/sandbox/secrets.py:7-8` (`_NAMES`), espelhando
`.harness/sprint-2026-09-18/story-CHAT-TOOLS-CONTRACT/contract.md:218-221`.
**Stories:** CHAT-TOOLS-CONTRACT (a spec que estreitou) + CHAT-TOOLS-BE (a implementação fiel a ela).

O código implementa **exatamente** o que o contrato v1.1 §4 manda — essa parte está certa. O
problema é que o contrato estreitou o que o threat model tinha prometido, sem justificativa
registrada: o threat model (§2, linha da denylist) promete `id_*`; o contrato e o código entregam
`id_rsa*` e `id_ed25519*`.

Reproduzido contra `requires_approval()` (chaves ECDSA/DSA e arquivos de credencial comuns passam
**sem gate de aprovação**):

```
free  id_ecdsa            free  .npmrc      free  .kube/config
free  id_dsa              free  .netrc      free  .docker/config.json
free  .pypirc             free  terraform.tfstate
```

(Para referência, o que funciona: `.env`, `.env.local`, `sub/.env`, `config/credentials.json`,
`.ssh/id_rsa`, `.aws/credentials`, `.git/config`, `*.pem`, `*.key`, `*.kdbx`, `secrets.yaml`,
`my_secret_notes.txt` — todos exigem aprovação, corretamente.)

**Risco:** `read` é automático (não passa pelo gate). Uma injeção indireta (T3, o ator que o
próprio threat model chama de "o mais provável deste sprint") induz o modelo a ler um desses
arquivos, sem clique do usuário, e o conteúdo vai para o provider remoto. A contenção de raiz
segura os que moram em `%USERPROFILE%`; os que moram dentro de um repo — `.npmrc`,
`.docker/config.json`, `.pypirc`, `terraform.tfstate` — não têm essa proteção.

**Fix:** acrescentar a `_NAMES` / à lista de diretórios: `id_*` (substituindo os dois específicos),
`.npmrc`, `.netrc`, `_netrc`, `.pypirc`, `*.tfstate`, `*.tfstate.backup`, `*.tfvars`, e `.docker`
e `.kube` à tupla de diretórios em `secrets.py:29`. Atualizar `contract.md:218-221` na mesma
mudança, para spec e código não divergirem de novo.

### P2-2 — A redação de saída falha em chave entre aspas (JSON/XML), que é o formato mais comum

**Local:** `backend/sandbox/secrets.py:17` (regra `assignment`), espelhando `contract.md:224`.
**Stories:** CHAT-TOOLS-CONTRACT + CHAT-TOOLS-BE.

A regra é `(?i:api[_-]?key|token|secret|password)\s*[=:]\s*\S{8,}`. Ela exige que o separador venha
logo depois do nome — qualquer aspa no meio quebra o match. Reproduzido:

```
1  api_key=sk-whatever12345678        -> [redacted:assignment]
1  API_KEY: sk-whatever12345678       -> [redacted:assignment]
1  export TOKEN="abcdefghijklmnop"    -> export [redacted:assignment]
0  "api_key": "sk-whatever12345678"   -> "api_key": "sk-whatever12345678"   <-- passa cru
0  "token": "abcdefghijklmnop"        -> "token": "abcdefghijklmnop"        <-- passa cru
0  'password': 'hunter2hunter2'       -> 'password': 'hunter2hunter2'       <-- passa cru
0  <password>hunter2hunter2</password> -> <password>hunter2hunter2</password> <-- passa cru
```

Efeito em arquivos reais (conteúdo devolvido **verbatim**, 0 redações):

```
.docker/config.json   LEAKS VERBATIM   {"auths":{"ghcr.io":{"auth":"<base64 user:senha>"}}}
terraform.tfstate     LEAKS VERBATIM   {"outputs":{"db":{"value":{"password":"s3cr3t-prod-pw"}}}}
.netrc (senha comum)  LEAKS VERBATIM   machine internal.corp / login x / password Tr0ub4dor&3xx
```

Prefixos de chave que também passam cru: `sk-ant-…` (Anthropic — o regex `sk-[A-Za-z0-9]{20,}`
para no primeiro hífen), `sk-proj-…` (OpenAI atual), `ghs_`/`gho_`/`github_pat_` (só `ghp_` está
coberto), e `client-key-data:` do kubeconfig.

**Por que isso importa mais do que parece:** o §4 do threat model mantém essa camada justamente
porque "é a única camada que age *depois* de uma aprovação errada" (T5, fadiga de aprovação, que
o mesmo documento aponta como o caminho de ataque mais barato que sobra). Ela é a rede de
segurança de `exec` aprovado — e `docker inspect`, `npm config list --json`,
`kubectl get secret -o json`, `aws configure export-credentials` imprimem exatamente o formato que
ela não pega.

**Fix:** trocar `\s*[=:]\s*` por `["']?\s*[:=]\s*["']?` na regra `assignment`; acrescentar
`sk-ant-[A-Za-z0-9-]{20,}`, `sk-proj-[A-Za-z0-9_-]{20,}`, `gh[posu]_[A-Za-z0-9]{20,}`,
`github_pat_[A-Za-z0-9_]{20,}` a `_PATTERNS`; e um caso negativo novo em
`backend/tests/test_sandbox_secrets.py` para não redigir prosa normal ("a line about tokens"
continua com 0 redações hoje — bom, manter).

**Severidade P2, não P1, e o porquê:** o controle primário (contenção de raiz) não falhou; `exec`
continua sempre gated; auth continua fechada; cada `read` aparece no transcript. O que falhou é a
camada de profundidade. Vira P1 se aparecer um caminho em que um segredo saia **sem** exigir nem
conteúdo hostil dentro do workspace autorizado nem uma aprovação errada — não achei nenhum.

### P3 (backlog, documentar no PR)

1. **`shutil.which` no Windows prefixa o cwd do processo** — `backend/sandbox/exec.py:37`. O
   executável é resolvido com o PATH e o cwd **do sidecar**, não do workspace, então um binário
   plantado no repo do usuário não é escolhido (bom). Ainda assim, resolver contra um `scrub_env()`
   PATH explícito seria mais previsível.
2. **Janela entre spawn e Job object** — `exec.py:69-71`: `create_subprocess_exec` e depois
   `tree.attach(proc.pid)`. Um filho que forke um neto nesse intervalo escapa do Job. Mitigado na
   prática pelo `taskkill /T /F` em `adapters/cli_shared.py:218`. Fechar de verdade exigiria
   `CREATE_SUSPENDED` + resume após o attach.
3. **TOCTOU entre `resolve_in_root` e `open`** — `sandbox/read.py:18` vs `:26`. Exige quem já
   escreve no workspace, ou seja, o T2 que o threat model aceita como R1. Anotado, não acionável.
4. **Persistência sem redação quando não há broker** — `routers/execution.py:664`:
   `redact_value(data) if broker else data`. Um run direto **sem** tools persiste a saída do modelo
   crua no `ExecutionLog`. É DB local, mas a assimetria não tem motivo — redigir sempre custa o
   mesmo.
5. **`FileSecrets` deriva a chave Fernet do caminho do store** — `backend/secret_store/file_store.py:22-31`.
   O caminho não é segredo, então quem lê os arquivos deriva a chave. O módulo já diz isso e
   recomenda `OH_SECRETS=keychain`. **Pré-existente** — esta sprint só moveu o arquivo, conteúdo
   byte-idêntico (`git diff -M` confirma rename puro). Fora de escopo, registrado.
6. **`test_usage_routes_require_the_token_too` falha quando o módulo roda isolado** —
   `backend/tests/test_sidecar_auth.py:61`, `sqlite3.OperationalError: no such table: budget_config`
   (a request chega ao router porque a fixture de init do DB só roda com a suíte inteira coletada).
   Na suíte completa passa (608 passed). **Não é falha de segurança**: verifiquei a propriedade em
   si ao vivo, `/usage/summary` sem token dá 401. É higiene de teste — um teste de fronteira de
   auth deveria ser válido isolado, que é justamente quando alguém o roda para checar uma suspeita.

### Nota positiva (vale registrar)

A renomeação `backend/secrets/` → `backend/secret_store/` não é cosmética: o pacote antigo
**sombreava o módulo `secrets` da stdlib** e reimplementava o carregamento dele à mão
(`git show 3689da0:backend/secrets/__init__.py`, 75 linhas de `_load_stdlib_secrets()` com busca
manual por `Lib/secrets.py`). O mesmo `secrets` da stdlib é o que
`backend/security/sidecar_token.py:37` usa para gerar o token do sidecar com
`secrets.token_urlsafe(32)`. Trocar uma monkey-patch frágil no caminho de geração de token por um
nome de pacote que não colide é endurecimento real, não arrumação. Sem import órfão sobrando
(grep por `from secrets`/`import secrets` em `backend/` fora de `.venv` só acha a stdlib legítima).
