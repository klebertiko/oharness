### Persistência no navegador — checado porque `read` traz conteúdo de arquivo

`readDisclosure.ts:34` usa `create()` puro, **sem** middleware `persist` — a store de disclosure é
memória de sessão, some no reload, e o brief está certo em tratá-la como UX informativo e não como
controle de segurança. Confirmei também que nada do caminho de tools vai para o `localStorage`: as
três stores persistidas (`grep -rn "persist(" src/store/`) são `chatProviderStore`, `workspaceStore`
e `threadStore`, e o shape persistido do `threadStore` (`threadStore.ts:15-30`) guarda
`content`/`providerLabel`/`runId` — **não** guarda `RunState`, `blocks` nem `ToolCall`. Resultado de
tool vive só em memória no cliente e, redigido, no `ExecutionLog` do backend. Correto.

A própria frase revelada (`readDisclosure.ts:22`, `arquivos lidos são enviados a ${connection.provider}`)
interpola apenas o rótulo do provedor do catálogo — não vaza caminho, conteúdo, chave nem endpoint.

### `splitArgv` não tenta ser esperto — confirmado

`chatCommands.ts:51-74` é um tokenizador e nada mais. Li caractere a caractere: aspas duplas
agrupam, `\` escapa o próximo caractere **apenas dentro** de aspas, espaço separa. Não há expansão
de variável (`$VAR`, `%VAR%`), nem `~`, nem substituição de comando (`` ` ``, `$()`), nem glob, nem
`spawn`/`exec`/`eval` em lugar nenhum do FE. Operadores de shell (`|`, `&&`, `>`, `;`, …) são
mantidos como itens argv **literais** e devolvidos em `shellSyntax`, e `ChatComposer.tsx:23` troca o
envio por um aviso em vez de mandar a coisa adiante. Isso está alinhado com `shell=False` no
backend: o FE compõe, o backend executa.

Nota sem severidade: aspas **simples** não agrupam (`/exec python -c 'import os'` vira quatro itens
com aspas grudadas). É divergência do shlex real, mas cai do lado seguro — nada é agrupado
escondido, e o card mostra o argv literal um item por linha, então o usuário vê exatamente o que vai
rodar. Não é achado.

## Achados

### P2-FE-1 — Card de aprovação replayado envia decisão viva para outro run

**Onde**
- `frontend/src/components/agent-run/Transcript.tsx:86` — `const runId = useActiveRunStore((s) => s.runId);`
- `frontend/src/components/agent-run/Transcript.tsx:100` — `<ToolCard call={call} runId={runId} connection={connection} />`
- `frontend/src/components/agent-run/HistoricalRunDetail.tsx:78` — `<Transcript run={run} onResolve={() => undefined} />`

`ToolRow` puxa o id do run da store **global de run ativo**, não do run que ele está desenhando.
Na visão ao vivo isso coincide. Em `HistoricalRunDetail`, que replaya um `ExecutionLog` persistido
pelo mesmo reducer e pelo mesmo `Transcript`, não coincide: o card pertence ao run A e o botão
dispara contra o run B.

**Por que é alcançável** (o estado "pendente" sobrevive ao replay)

1. `backend/routers/execution.py:673-681` — quando o cliente desconecta (fechar a aba, recarregar,
   navegar) com o run parado no gate de aprovação, o `except asyncio.CancelledError` emite
   `run_stopped` e `harness_done` mas **não** emite `tool_denied` para a call pendente. O
   `tool_approval_required` já foi para a lista `events` (`:546`), e o `finally` com
   `anyio.CancelScope(shield=True)` grava tudo (`:697`). O log persistido fica com um gate pendurado.
2. No replay, `runReducer.ts:205` marca `call.approval` sem `decision`; nem `run_stopped`
   (`runReducer.ts:367`) nem `harness_done` (`:370`) tocam em `blocks` ou em `call.approval`.
3. `ToolCard.tsx:48` → `pendingApproval === true`. `ToolCard` não olha `run.status` em momento
   algum, só a call e o `runId` global. Botões **Aprovar/Rejeitar** vivos, num run morto.

**Impacto**

`backend/routers/execution.py:743` entra no ramo de tool só se `control.tool_mode` — e
`control.tool_mode = tool_options is not None` (`:524`). Então:

| Estado do run vivo | O que acontece ao clicar "Aprovar" no card histórico |
|---|---|
| nenhum run vivo | `runId` é `null` → botões `disabled` (`ToolCard.tsx:97,99`). Inofensivo, só confuso. |
| run vivo **com** tools | `tool_approval.decide()` com `call_id` estranho → `ApprovalConflict` → 409. **Fail-closed.** |
| run vivo **sem** tools | `tool_mode` é `False`, o ramo é pulado, cai em `execution.py:751-753`: `control.decision = {"decision": "approve"}` + `control.release()`, **descartando o `call_id` em silêncio**. O gate HITL do run vivo é aprovado por um clique num card histórico de outra execução. |

A última linha é a falha. O `call_id` ser opcional no control legado do nó HITL é comportamento
**conforme o contrato** (§2.6, explícito), então o backend não está errado — quem erra é o FE, que
renderiza controle vivo para um run que não é o vivo.

**Severidade: P2.** Não é P1: não há gatilho controlado por atacante, exige o clique do próprio
usuário num card que ele teria de ler errado, e o desfecho é aprovar um gate HITL que ele já está
supervisionando. Mas é confusão de autorização real, em código entregue, e o conserto é pequeno.

**Fix (FE, @FE)** — duas metades, ambas locais:
1. Passar o id do run **do próprio card**: `RunState.runId` já existe e já é preenchido em
   `runReducer.ts:108`. `ToolRow` deve recebê-lo do `run` que o `Transcript` renderiza em vez de ler
   a store global.
2. Não renderizar controle vivo para um run que não está vivo: quando o run do card não é o run
   ativo (ou `run.status` é terminal), mostrar um estado terminal — algo como *"não decidido — a
   execução terminou"* — em vez de Aprovar/Rejeitar. Isso também conserta o caso "nenhum run vivo",
   onde hoje o usuário vê um card que diz "aguardando aprovação" para sempre.

Teste de trava sugerido junto: replay de um log com `tool_approval_required` sem decisão não
renderiza botão habilitado, com um run ativo na store.

### P2-FE-2 — Token do sidecar é anexado por prefixo de string, não por origem

**Onde:** `frontend/src/lib/apiBase.ts:85` — `if (url.startsWith(apiBase()))`

Código novo desta sprint (bloco inteiro, +50 linhas em `03c91ba`), e é o mecanismo do qual
`chatToolsApi.ts` e `runClient.ts` dependem para autenticar. O patch é global em `window.fetch`
(`:83`), então vale para **toda** chamada do app, não só as do broker.

`apiBase()` devolve `http://127.0.0.1:8000` (sem barra final). `startsWith` sobre isso é satisfeito
por URLs que não são o sidecar. O caso limpo é o userinfo:

```
http://127.0.0.1:8000@attacker.tld/x
```

`startsWith("http://127.0.0.1:8000")` → `true`, mas o host real é `attacker.tld`. O
`Authorization: Bearer <token do sidecar>` vai junto para o host remoto. Como o patch é global,
qualquer `fetch` com URL influenciada por usuário ou por conteúdo leva o header. Existe superfície
de URL editável: `endpoint.editable: true` para `openai` (`catalog.ts:138`) e para `ollama`
(`catalog.ts:161`).

**Severidade: P2, não P1.** O impacto real é contido: o token só abre um sidecar em loopback, que
um host remoto não alcança de fora; e quem tem execução local para forjar a URL já podia ler o
arquivo do token — que é exatamente o risco R1/T2 que o threat model aceita. O que sustenta o P2 é
que o defeito é do tipo que vira P1 no dia em que `apiBase()` deixar de ser loopback (o próprio
`apiBase.ts:8` prevê `window.__OH_API__` injetado pelo Tauri), e o conserto é de uma linha.

**Fix (FE, @FE)** — comparar origem, não prefixo:

```ts
let target: URL;
try { target = new URL(url, location.href); } catch { return nativeFetch(input, init); }
if (target.origin === new URL(apiBase()).origin) { /* anexa o header */ }
```

Teste negativo junto: `http://127.0.0.1:8000@evil.test/x` e `http://127.0.0.1:80001/x` **não**
recebem `Authorization`.

### P3 (backlog, documentar no PR)

1. **O card pode pedir aprovação sem mostrar comando nenhum** — `ToolCard.tsx:73-79`. O render é
   `call.argv ? <ol> : call.path ? <p> : null`. Se `args` não produzir nem `argv` nem `path`
   (`parseToolArgs`, `runReducer.ts:65-76`), o card ainda mostra a frase "Isto é execução local, com
   os seus privilégios" e os botões Aprovar/Rejeitar — **sem nada para ler**. E ele já tem a string
   crua em `call.args` (`types.ts:7`, preenchido em `runReducer.ts:168`), só não a usa como
   fallback. Não é alcançável hoje: `backend/sandbox/broker.py:82-85` só emite
   `tool_approval_required` **depois** de `validate_call` passar nos schemas estritos `Exec`/`Read`
   (`backend/sandbox/schemas.py:40-44`), então `argv`/`path` sempre existem. Fica como defesa em
   profundidade, porque o threat model faz do argv literal um **requisito** do card (B5/T5), e um
   card que falha aberto contra esse requisito não deveria existir. Fix: renderizar `call.args` (ou
   um aviso explícito) quando nada parseia.
2. **A disclosure de leitura confia no rótulo do catálogo, não no endpoint real** —
   `readDisclosure.ts:19` suprime a frase quando `connection.residence === "local"`. Só que
   `ollama` tem `residence: "local"` fixo (`providerStore.ts:172`) e `endpoint.editable: true`
   (`catalog.ts:161`). Apontar a conexão "Ollama" para um host de LAN ou um túnel manda o conteúdo
   dos arquivos para fora da máquina **sem** a frase aparecer. É UX informativo e foi o próprio
   usuário que trocou o endpoint, por isso P3 — mas o honesto é chavear pelo host resolvido ser
   loopback, não pelo rótulo.
3. **Bundle de dev carrega o token vivo, e o `next` fixado tem advisory de dev server** — a guarda
   em `next.config.ts:51` protege produção (verifiquei: 0 ocorrências em `frontend/out`), mas
   `npm run dev` assa o token real no bundle. Entre os advisories do `next` está
   `GHSA-3h52-269p-cp9r` — *information exposure no dev server por falta de verificação de origem*.
   Os dois juntos formam uma cadeia concreta na máquina de quem desenvolve. Não afeta o produto
   entregue e o próprio comentário do arquivo já diz que não é o desenho de produção; o conserto
   (bump do `next`) é de quem manda no `package.json`, não destas duas stories.
4. **`sendControl` é fire-and-forget** — `ToolCard.tsx:56`, `void sendControl(...)`, e
   `runClient.ts:125-129` não checa `res.ok`. Um 409/401/erro de rede deixa o card preso em
   "enviando…" com os dois botões desabilitados (`ToolCard.tsx:97,99,103`), e gera rejeição de
   promise não tratada. Falha fechado (o backend expira em 10 min e nega), então engana em vez de
   expor — mas quem clicou "Rejeitar" merece saber que a rejeição não chegou.
5. **Ponteiro de doc obsoleto** — `next.config.ts:21` diz que o token é "read by
   `src/lib/apiAuth.ts`". Esse arquivo não existe; o código está em `apiBase.ts:73-94`. Só doc.
