OHarness Model · technical reference

An open document to describe harnesses.

The OHarness Model (OHM) describes how a harness is composed: participants, knowledge, capabilities, relationships, execution parameters, and human control points. The adopted authoring format is YAML 1.2, with the extension .ohm; the APIs stay JSON. The Studio migration is not implemented yet: today, importing and exporting .ohm files in the desktop app reads and writes JSON.

Document contract.

A .ohm file is a declarative UTF-8 document. YAML is the human-authoring representation; after parsing, its content converges to a shared normalized model. The format is not an executable, a language model, or implicit authorization to run scripts.

schemaVersion
Version of the data contract. It does not identify YAML or JSON syntax.
manifest
Harness identity, version, description, declared license, and taxonomy.
graph
Participants (nodes) and explicit relationships (edges), referenced by stable identifiers.
content
Embedded artifacts such as prompts, agents, skills, hooks, commands, and scripts.
runtime
Execution preferences, CLI, environment, and secret references. Credentials do not belong in the document.
validation
The simulation profile (mockProfile) of the document.

YAML anchors and aliases do not represent topology. Cycles in the data graph do not, by themselves, grant repetition semantics: loops require an explicit contract for conditions, budgets, timeouts, cancellation, per-iteration state, and human intervention.

Minimal document.

The document below shows structure 1.0.0. The empty graph and multiline prompt are declarative data; no content is executed when the file is opened or validated. The license belongs to the document and does not declare the app's license.

hello.ohm
# OHM in YAML 1.2 — declarative contract.
schemaVersion: "1.0.0"
manifest:
  id: hello
  name: Hello
  version: "0.1.0"
  description: Minimal OHarness Model document.
  license: MIT
  tags: []
graph:
  nodes: []
  edges: []
content:
  prompts:
    objective: |-
      Describe the objective of the work.
      Define the evidence required to accept the result.
  agents: {}
  skills: {}
  hooks: {}
  commands: {}
  scripts: {}
runtime:
  preferred: api
  cli: null
  env: []
  secrets: []
validation:
  mockProfile: default

Validation, today.

The app's sidecar validates an .ohm file in layers: first the JSON Schema, which checks the shape of the fields; then the graph rules, where every node has a non-empty, unique text identifier and every edge points at existing nodes; finally, the backend's typed model. The command line does the same for YAML and JSON: python -m oharness validate <file>.

Simulation (Plan simulation) produces a deterministic step plan by ordering the graph topologically. It calls no models and does not run the embedded content. A graph with a cycle can pass structural validation and fail simulation: graphs with cycles are not executable in this version.

A structurally valid document does not prove the quality of the instructions, provider availability, script safety, or fitness for production. The HITL node pauses an app run until someone approves or rejects, and rejecting stops it. That is a feature of the app's engine, not a guarantee from any other tool that reads the file.

Probabilistic decisions are advisory, not sovereign.

Laya is an experimental local classifier. It needs a separate process on loopback and is advisory only. With it running, a chat message goes to Laya first, which chooses between answering directly and starting the harness; below 0.80 confidence, or without Laya available, model-based triage decides. A Laya decision node in a graph is evidence only: no gate, edge, or HITL step reads that result.

In the repository's continuous integration, Laya can also run in shadowmode, producing advisory evidence for issue triage, with no authority over merge or release.

No classifier replaces the schema, the graph rules, the gates, or the human decision.

Scope and maturity.

The adopted decision is YAML 1.2 for authoring, with JSON in the API contracts. Already on YAML: the harnesses bundled in the app that ship as .ohm files, the backend codec, and the command line. Still on JSON: importing and exporting .ohm files in Studio, because the desktop migration is not finished. The plan does not promise to preserve comments or the style of the input file.

The ability to represent a graph is distinct from the ability to execute it. Loop semantics, complete portability, cross-tool round trips, and operational equivalence require their own contracts and tests; they are not automatic consequences of the format choice.

OHM is an evolving technical proposal from OHarness. It is not yet an independent standard, has no formal governance, and no adoption beyond the project itself. Openness and interoperability are goals, not facts.

The manifesto presents the institutional principles guiding that evolution.
