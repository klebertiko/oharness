# OHarness v0.0.1-alpha (pre-release)

The product was renamed from OpenHarness to **OHarness** before this release (PR #144): installers, packages, the Tauri identifier and links all use the new name.

**First public build. Alpha quality, installers are UNSIGNED.** Read "Unsigned installers" before you run anything.

## What it is

OHarness is a desktop app (Tauri v2 shell, Next.js static export, FastAPI sidecar on loopback) for authoring and running **harnesses**: systems of Agents, Gates, HITL checkpoints, Skills and Signals. A harness is saved as an OHarness Model (`.ohm`) file. **Nilo** is the assistant that drafts harnesses in Studio. You bring your own providers; there is no OHarness cloud for inference.
<!-- proof: CONTEXT.md (terms), README.md "What this is", src-tauri/tauri.conf.json, backend/main.py -->

## What is in 0.0.1-alpha

**Studio**
- **Ask Nilo** (`Mod+I`): describe a flow, review the proposed graph edits, **Keep** or **Undo** (one undoable step). With no provider ready it falls back to a deterministic planner, tagged "Offline draft". In the Inspector, **Assist** drafts, improves or reviews text fields. <!-- frontend/src/components/copilot/{CopilotPanel,ProposalCard}.tsx; backend/studio_copilot/{mock_planner,field_assist}.py; backend/routers/studio_{copilot,assist}.py; PR #63, #66 -->
- **Bundled harnesses**, each opened as an editable copy (the bundled one is never changed): Agile Harness, DeepSeek Harness, Matt Pocock skills. Also a minimal "Agent + review" starting point. <!-- backend/oharness/examples.py; frontend/src/lib/studioExamples.ts, templates.ts; StudioActionsBar.tsx; PR #91, #124 -->
- **Canvas** with **Auto-arrange graph** (`Shift+L`, layered layout via dagre). <!-- frontend/src/lib/graphLayout.ts, components/canvas/CanvasDock.tsx; docs/adr/0007-graph-auto-layout.md; PR #107 -->
- **Files**: New, Save, Save as, Discard, Delete, Import and Export of `.ohm`. The desktop app uses the native Save dialog on Export. <!-- StudioActionsBar.tsx, lib/ohmFile.ts, lib/studio.ts; PR #95 -->
- **Validate** and **Plan simulation**: structural validation against the OHM schema (ids, edge references) and a deterministic step plan, both served by the sidecar. <!-- ValidateDock.tsx; backend/routers/bundles.py (/bundles/validate, /bundles/mock); backend/oharness/{validate,mock_run}.py -->
- **Mock run** (no provider called) with a **human approval gate**: a HITL node stops the run until you approve or reject, and the decision stays in the transcript. A **Connected** mode runs each node with its pinned provider. <!-- Toolbar.tsx MODES; backend/engine.py hitl_pause/hitl_resolved; routers/execution.py /execute/{run_id}/control; components/agent-run/Gate.tsx -->

**Chats**
- Direct runs and harness-bound conversations, with a per-chat provider and workspace folder. <!-- components/agent/{ChatProviderPicker,WorkspacePicker}.tsx -->
- **Permission modes per chat: Ask (default), Auto, Plan**, enforced by the sidecar, not the UI. Ask: every command waits for you. Auto: an explicit allowlist of read-only `git`, `ls`, `pwd` runs unasked; `npm`/`pnpm`/`yarn` and `pytest` run unasked only in a workspace you marked trusted. Plan: read-only, commands refused. There is no bypass mode. <!-- backend/sandbox/permission.py; frontend/src/lib/permissionMode.ts; PR #102 -->
- **Chat tools** `/exec`, `/read`, `/ls` go through a backend broker: path containment inside the workspace, per-action approval in Ask mode (Auto runs only its allowlist unasked), output redaction of secret-like values, call and size limits (8 tool calls per turn, 256 KiB per read, 60 s default exec timeout). <!-- backend/sandbox/{broker,paths,secrets,capabilities}.py; docs/adr/0004-chat-tools-broker.md; PR #114, #121/#122, #125 hardened git handling -->
- Collapsible activity summary in the transcript. <!-- PR #99 -->

**Providers**
- Six connections: Anthropic (local `claude` CLI), OpenAI (local `codex` CLI), OpenRouter (API key), Ollama local (daemon on this machine), Ollama Cloud (API key), Cursor (local `cursor-agent`, Agent-only). Per-node pins with ordered failover; a run never silently swaps provider. <!-- backend/adapters/catalog.py, cli_*.py, openai_compatible.py; docs/product/provider-harness-rule.md; PR #31, #66 -->
- Keys are stored by the sidecar in a local file store (Fernet, key derived from the store path), under `secrets` in the app's data folder (`%LOCALAPPDATA%\dev.oharness.app\secrets` on Windows; a new folder since the rename, see Known limitations); the Tauri shell never writes them. This keeps keys out of casual reach but does not protect them from another process running as your user; a keychain store exists (`OH_SECRETS=keychain`) but the desktop sidecar defaults to the file store. <!-- backend/sidecar_entry.py, secret_store/file_store.py -->
- Usage summary and a budget setting. <!-- backend/routers/usage.py; components/providers/usageStore.ts -->

**Desktop**
- Every screen was redesigned on the OHarness design system (PR #141); the website captures show that UI.
- NSIS per-user installer on Windows; AppImage and `.deb` on Linux; DMG on macOS (Apple silicon and Intel). The sidecar listens on loopback only and every route but `/health` needs a per-process bearer token. <!-- release.yml; backend/main.py; PR #110 -->

## What is NOT in 0.0.1-alpha

- **No signed installers** (see below). No auto-update.
- **Automate and Pull requests do not exist.** Their routes were removed. <!-- README.md "Removed"; PR #31 -->
- **No live-provider test matrix.** The Connected mode and all six connections are implemented, but this release makes no claim that each was exercised end to end on every OS. CI exercises the mock path, the packaged sidecar and the Windows desktop smoke only. <!-- release.yml smoke steps; docs/ci-security.md#releases -->
- **`.ohm` YAML is not finished on the desktop.** The bundled `.ohm` files, the backend codec and the CLI use YAML 1.2; Studio Import and Export still read and write JSON text inside the `.ohm` file. <!-- frontend/src/lib/studio.ts importOhmText (JSON.parse), bundlesApi.ts serializeBundle (JSON.stringify); docs/product/ohm-yaml-migration.md; docs/adr/0003-ohm-yaml.md -->
- **Graphs with cycles are not executable.** Validation checks structure, not acyclicity; the engine orders nodes topologically and reports unreachable ones. Loops are a planned capability, not shipped. <!-- docs/product/ohm-yaml-migration.md P2; backend/engine.py -->
- **Laya** (local classifier for the front door and decision node) is experimental, needs a separate process, and is advisory only. <!-- README.md Providers; docs/adr/0005, 0006 -->
- Chat command execution is **not an OS sandbox**: approved commands run with your user's privileges. <!-- docs/adr/0004-chat-tools-broker.md "Consequências" -->
- Researched or designed but not implemented: Workspace Manager (PR #139), durable run history (PR #137), chat/provider recovery work (PR #136, issues #82-#90). Not in this tag.

## System requirements

**Below the minimum, the interface renders broken, with no warning.** The UI uses Tailwind CSS 4 (migration in PR #120), which requires Chrome 111, Safari 16.4 or Firefox 128 or newer because of `@property` and `color-mix()`. On macOS and Linux the app renders in the system WebView; if that is older, the layout breaks and the app shows no message. On Windows, WebView2 tracks the current Edge and meets the minimum. <!-- proof: https://tailwindcss.com/docs/compatibility and /docs/upgrade-guide (V); MDN browser-compat-data css/at-rules/property.json, css/types/color.json (V); https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution (V); no WebView check in src-tauri; PR #120 open when written -->

| System | Minimum |
| --- | --- |
| Windows | Windows 10 or 11, 64-bit (x64) only, with the WebView2 Runtime (Evergreen). Windows 11 includes it; Windows 10 from version 1803 already ships it (Tauri docs). If it is missing, the NSIS installer downloads the WebView2 bootstrapper and needs an internet connection. Windows 7, 8 and 8.1 do not qualify: their WebView2 stopped at Edge 109. <!-- proof: src-tauri/tauri.conf.json (nsis, no webviewInstallMode, default downloadBootstrapper); release.yml windows-x64 only; https://v2.tauri.app/start/prerequisites/; https://learn.microsoft.com/en-us/deployedge/microsoft-edge-supported-operating-systems --> |
| macOS | macOS 13.3 or newer, Apple silicon (arm64) or Intel (x64), one native installer each (not universal). 13.3 is the defensible floor: macOS 13.0 to 13.2 ship Safari 16.1 to 16.3, without `@property`. Today this is documentation only: declaring it in the installer (`LSMinimumSystemVersion`) is in PR #167 and takes effect only after it; until then macOS does not stop the app from opening on an older version. <!-- proof: release.yml macos-15 / macos-15-intel; tauri.conf.json has no bundle.macOS.minimumSystemVersion (Tauri default 10.13); https://v2.tauri.app/reference/config/ --> |
| Linux | x86_64 (64-bit), WebKitGTK 2.40 or newer (`webkit2gtk-4.1`) and glibc 2.35 or newer (Ubuntu 22.04+, Debian 12+, Fedora 36+, per the comment in `release.yml`). Ubuntu 22.04 without updates ships WebKitGTK 2.36, below the floor; with security updates it ships 2.50.x. The `.deb` depends on `libwebkit2gtk-4.1-0` and, after PR #167, on `(>= 2.40)`; before that it requires no version. <!-- proof: release.yml ubuntu-22.04 build, appimage+deb; https://launchpad.net/ubuntu/+source/webkit2gtk; https://v2.tauri.app/distribute/debian/ --> |

**Not verified:** Apple does not literally state that macOS 13.3 ships Safari 16.4 (secondary source only); whether an app's WKWebView on macOS 12 or earlier gets a manually installed Safari 16.4; the real minimum (`minos`) of the packaged macOS binaries, including the PyInstaller sidecar, which may be higher than 13.3; what macOS does exactly when it opens an app below `LSMinimumSystemVersion`; that WebKitGTK 2.40 is equivalent to Safari 16.4 with `@property` enabled by default (2.40 is a plausible floor, not a proven one); whether the AppImage carries its own WebKit (per the Tauri bundler's code it does; our file was not inspected); the effect of `(>= 2.40)` on the generated `.deb`; the WebKitGTK version of Fedora 36 and of distros not listed. The installers are unsigned: see below, and download only from the tag page linked at the end, never `/releases/latest`.

## Unsigned installers

None of the installers is code-signed or notarized. The build signs a platform only when its secrets exist in the `release` environment. <!-- release.yml signing steps; docs/ci-security.md#code-signing -->

| Platform | File | What you will see |
| --- | --- | --- |
| Windows 10/11 x64 | `OHarness-windows-x64-setup.exe` | SmartScreen: "Windows protected your PC", unknown publisher. Choose *More info*, then *Run anyway*. Needs the WebView2 Runtime (present on current Windows 10/11). |
| macOS Apple silicon | `OHarness-macos-arm64.dmg` | Ad-hoc signature only, not notarized. Gatekeeper blocks the first launch. *System Settings > Privacy & Security > Open Anyway*, or `xattr -dr com.apple.quarantine /Applications/OHarness.app` after verifying the file. |
| macOS Intel | `OHarness-macos-x64.dmg` | Same as Apple silicon. |
| Linux x86_64 | `OHarness-linux-x86_64.AppImage`, `OHarness-linux-amd64.deb` | No warning and no embedded signature. Built on Ubuntu 22.04: needs glibc 2.35 or newer (Ubuntu 22.04+, Debian 12+). |

Verify every download before you run it, in the folder with the files:

```bash
sha256sum --check --ignore-missing SHA256SUMS
gh attestation verify OHarness-windows-x64-setup.exe --repo klebertiko/oharness
```

Use the file you downloaded in the second command. `OHarness-sbom.cdx.json` is the CycloneDX SBOM; every installer carries a build-provenance and an SBOM attestation. Attestations prove where a file was built; they do not replace a publisher signature.

## Known limitations

- **No WebView minimum is enforced yet.** The requirements above are documentation: the installer does not check the OS WebView version (the macOS and `.deb` declarations are in PR #167), and rendering still varies between WebView2, WKWebView and WebKitGTK. <!-- docs/adr/0001-desktop-packaging.md lines 67 and 111; no minimum in tauri.conf.json -->
- **macOS and Linux desktops were built and had their sidecar smoke-tested in CI, but the app window was never launched there by the maintainer pipeline.** The desktop smoke (window, health, clean exit) runs on Windows only, and its WebView probe is best-effort on hosted runners. <!-- release.yml lines 174-250, 462-465; docs/ci-security.md#releases -->
- **Data location:** the desktop shell starts the sidecar with `OH_DATA_DIR` set to its app-local data directory, which is named after the Tauri identifier: `%LOCALAPPDATA%\dev.oharness.app` on Windows (database `harness.db` and `secrets`), and the equivalent per-user folder on macOS and Linux (those paths were not verified here). `%LOCALAPPDATA%\OHarness` and `~/OHarness` apply only to a sidecar run on its own without `OH_DATA_DIR`. <!-- src-tauri/src/lib.rs spawn_sidecar (app_local_data_dir -> OH_DATA_DIR); backend/sidecar_entry.py _data_dir; src-tauri/tauri.conf.json identifier -->
- **Rename side effects (PR #144).** The Tauri identifier changed from `dev.openharness.app` to `dev.oharness.app`, so the app-local data folder changes with it: an installation of an earlier build keeps its `harness.db` and `secrets` in `%LOCALAPPDATA%\dev.openharness.app` (confirmed on the maintainer's machine), while the new build uses `%LOCALAPPDATA%\dev.oharness.app`. Nothing is moved automatically. The file store derives its key from the secrets path, so keys stored by an earlier build must be entered again. The compatibility code covers other cases only: OS keychain entries under the old service name `openharness` are read and migrated on first access; with `OH_SECRETS_DIR` unset (development runs), `~/.openharness/secrets` stays in use while `~/.oharness/secrets` does not exist; and `OPENHARNESS_BACKEND_URL` and `OPENHARNESS_CURSOR_WSL_*` still work as fallbacks of the `OHARNESS_*` variables. No public release existed under the old name. <!-- git show 4cdc868; backend/secret_store/{factory,keychain,file_store}.py; backend/sidecar_entry.py; src-tauri/tauri.conf.json -->
- Cursor on Windows runs inside WSL2 (default distro `Ubuntu-24.04`). <!-- README.md Providers; PR #80 -->
- Auto mode on Windows: reserved device names (`CON`, `NUL`, ...) as `ls`/`git` operands are not refused according to issue #109 (open, not blocking); worst case a command hangs until its timeout. A `.git` junction is now detected and asks instead of auto-approving (#146).
- Studio transcript with Nilo is session-only and replies are not streamed. <!-- README.md "Nilo in Studio" -->
- Public-preview licence: source-available for evaluation, redistribution terms not yet stated. <!-- README.md License -->
