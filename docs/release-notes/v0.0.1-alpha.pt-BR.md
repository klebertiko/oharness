# OHarness v0.0.1-alpha (pré-lançamento)

O produto foi renomeado de OpenHarness para **OHarness** antes desta versão (PR #144): instaladores, pacotes, o identificador do Tauri e os links usam o nome novo.

**Primeira versão pública. Qualidade alfa, os instaladores NÃO são assinados.** Leia "Instaladores sem assinatura" antes de executar qualquer coisa.

## O que é

O OHarness é um app desktop (casca Tauri v2, export estático do Next.js, sidecar FastAPI em loopback) para criar e executar **harnesses**: sistemas de Agents, Gates, checkpoints HITL, Skills e Signals. Um harness é salvo como um arquivo OHarness Model (`.ohm`). O **Nilo** é o assistente que rascunha harnesses no Studio. Você traz os seus próprios provedores; não existe nuvem do OHarness para inferência.

## O que há na 0.0.1-alpha

**Studio**
- **Ask Nilo** (`Mod+I`): descreva um fluxo, revise as mudanças propostas no grafo, **Keep** ou **Undo** (um passo desfazível). Sem provedor pronto, cai em um planejador determinístico, marcado "Offline draft". No Inspector, o **Assist** rascunha, melhora ou revisa campos de texto. <!-- frontend/src/components/copilot/{CopilotPanel,ProposalCard}.tsx; backend/studio_copilot/{mock_planner,field_assist}.py; backend/routers/studio_{copilot,assist}.py; PR #63, #66 -->
- **Harnesses incluídos (Bundled harness)**, cada um aberto como cópia editável (o original nunca muda): Agile Harness, DeepSeek Harness, Matt Pocock skills. Também um ponto de partida mínimo, "Agent + review". <!-- backend/oharness/examples.py; frontend/src/lib/studioExamples.ts, templates.ts; StudioActionsBar.tsx; PR #91, #124 -->
- **Canvas** com **Auto-arrange graph** (`Shift+L`, layout em camadas via dagre). <!-- frontend/src/lib/graphLayout.ts, components/canvas/CanvasDock.tsx; docs/adr/0007-graph-auto-layout.md; PR #107 -->
- **Arquivos**: New, Save, Save as, Discard, Delete, Import e Export de `.ohm`. O app desktop usa o diálogo nativo de salvar no Export. <!-- StudioActionsBar.tsx, lib/ohmFile.ts, lib/studio.ts; PR #95 -->
- **Validate** e **Plan simulation**: validação estrutural contra o schema OHM (ids, referências de arestas) e um plano de passos determinístico, ambos servidos pelo sidecar. <!-- ValidateDock.tsx; backend/routers/bundles.py (/bundles/validate, /bundles/mock); backend/oharness/{validate,mock_run}.py -->
- **Mock run** (nenhum provedor é chamado) com **aprovação humana**: um nó HITL interrompe a execução até você aprovar ou rejeitar, e a decisão fica na transcrição. O modo **Connected** executa cada nó com o provedor fixado nele. <!-- Toolbar.tsx MODES; backend/engine.py hitl_pause/hitl_resolved; routers/execution.py /execute/{run_id}/control; components/agent-run/Gate.tsx -->

**Chats**
- Execuções diretas e conversas ligadas a um harness, com provedor e pasta de workspace por chat. <!-- components/agent/{ChatProviderPicker,WorkspacePicker}.tsx -->
- **Modos de permissão por chat: Ask (padrão), Auto, Plan**, impostos pelo sidecar, não pela interface. Ask: todo comando espera por você. Auto: uma allowlist explícita de `git` somente leitura, `ls` e `pwd` roda sem perguntar; `npm`/`pnpm`/`yarn` e `pytest` rodam sem perguntar só em um workspace que você marcou como confiável. Plan: somente leitura, comandos recusados. Não existe modo de bypass. <!-- backend/sandbox/permission.py; frontend/src/lib/permissionMode.ts; PR #102 -->
- **Ferramentas do chat** `/exec`, `/read`, `/ls` passam por um intermediário no backend: contenção de caminhos dentro do workspace, aprovação por ação no modo Ask (o Auto só roda a allowlist sem perguntar), redação de valores que parecem segredos na saída, limites de chamadas e de tamanho (8 chamadas de ferramenta por turno, 256 KiB por leitura, 60 s de timeout padrão no exec). <!-- backend/sandbox/{broker,paths,secrets,capabilities}.py; docs/adr/0004-chat-tools-broker.md; PR #114, #121/#122, #125 hardened git handling -->
- Resumo de atividade recolhível na transcrição. <!-- PR #99 -->

**Providers**
- Seis conexões: Anthropic (CLI `claude` local), OpenAI (CLI `codex` local), OpenRouter (chave de API), Ollama local (daemon nesta máquina), Ollama Cloud (chave de API), Cursor (`cursor-agent` local, só para agentes). Fixação por nó com failover ordenado; uma execução nunca troca de provedor em silêncio. <!-- backend/adapters/catalog.py, cli_*.py, openai_compatible.py; docs/product/provider-harness-rule.md; PR #31, #66 -->
- As chaves são guardadas pelo sidecar em um arquivo local (Fernet, chave derivada do caminho do armazenamento), em `secrets`, na pasta de dados do app (`%LOCALAPPDATA%\dev.oharness.app\secrets` no Windows; pasta nova desde a renomeação, veja Limitações conhecidas); a casca Tauri nunca as grava. Isso tira as chaves do alcance casual, mas não as protege de outro processo rodando como o seu usuário; existe um armazenamento no chaveiro do sistema (`OH_SECRETS=keychain`), mas o sidecar do desktop usa o arquivo por padrão. <!-- backend/sidecar_entry.py, secret_store/file_store.py -->
- Resumo de uso e uma configuração de orçamento. <!-- backend/routers/usage.py; components/providers/usageStore.ts -->

**Desktop**
- Todas as telas foram redesenhadas sobre o design system do OHarness (PR #141); as capturas do site mostram essa interface.
- Instalador NSIS por usuário no Windows; AppImage e `.deb` no Linux; DMG no macOS (Apple silicon e Intel). O sidecar escuta só em loopback e toda rota, exceto `/health`, exige um token bearer por processo. <!-- release.yml; backend/main.py; PR #110 -->

## O que NÃO há na 0.0.1-alpha

- **Sem instaladores assinados** (veja abaixo). Sem atualização automática.
- **Automate e Pull requests não existem.** As rotas foram removidas. <!-- README.md "Removed"; PR #31 -->
- **Sem matriz de testes com provedores reais.** O modo Connected e as seis conexões estão implementados, mas esta versão não afirma que cada uma foi exercitada de ponta a ponta em todos os sistemas. A CI exercita só o caminho mock, o sidecar empacotado e o smoke do desktop no Windows. <!-- release.yml smoke steps; docs/ci-security.md#releases -->
- **O YAML do `.ohm` não está concluído no desktop.** Os `.ohm` incluídos, o codec do backend e a CLI usam YAML 1.2; Import e Export do Studio ainda leem e gravam texto JSON dentro do arquivo `.ohm`. <!-- frontend/src/lib/studio.ts importOhmText (JSON.parse), bundlesApi.ts serializeBundle (JSON.stringify); docs/product/ohm-yaml-migration.md; docs/adr/0003-ohm-yaml.md -->
- **Grafos com ciclos não são executáveis.** A validação checa estrutura, não aciclicidade; o motor ordena os nós topologicamente e aponta os inalcançáveis. Laços são uma capacidade planejada, não entregue. <!-- docs/product/ohm-yaml-migration.md P2; backend/engine.py -->
- **Laya** (classificador local para a porta de entrada e o nó de decisão) é experimental, precisa de um processo separado e é apenas consultiva. <!-- README.md Providers; docs/adr/0005, 0006 -->
- A execução de comandos do chat **não é um sandbox de SO**: comandos aprovados rodam com os privilégios do seu usuário. <!-- docs/adr/0004-chat-tools-broker.md "Consequências" -->
- Pesquisado ou desenhado, mas não implementado: Workspace Manager (PR #139), histórico durável de execuções (PR #137), trabalho de recuperação de chat/provedor (PR #136, issues #82-#90). Não estão nesta tag.

## Requisitos mínimos

**Abaixo do mínimo, a interface renderiza quebrada, sem aviso.** A interface usa o Tailwind CSS 4 (migração no PR #120), que exige Chrome 111, Safari 16.4 ou Firefox 128, ou mais novos, por causa de `@property` e `color-mix()`. No macOS e no Linux o app renderiza no WebView do sistema; se ele for mais antigo, o layout quebra e o app não mostra nenhuma mensagem. No Windows, o WebView2 acompanha o Edge atual e atende o mínimo. <!-- proof: https://tailwindcss.com/docs/compatibility e /docs/upgrade-guide (V); MDN browser-compat-data css/at-rules/property.json, css/types/color.json (V); https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution (V); nenhuma checagem de WebView em src-tauri; PR #120 aberto na data da escrita -->

| Sistema | Mínimo |
| --- | --- |
| Windows | Windows 10 ou 11, somente 64 bits (x64), com o WebView2 Runtime (Evergreen). O Windows 11 já o inclui; o Windows 10, a partir da versão 1803, já vem com ele (documentação do Tauri). Se faltar, o instalador NSIS baixa o bootstrapper do WebView2 e precisa de internet. Windows 7, 8 e 8.1 não atendem: o WebView2 deles parou no Edge 109. <!-- proof: src-tauri/tauri.conf.json (nsis, sem webviewInstallMode, padrão downloadBootstrapper); release.yml só windows-x64; https://v2.tauri.app/start/prerequisites/; https://learn.microsoft.com/en-us/deployedge/microsoft-edge-supported-operating-systems --> |
| macOS | macOS 13.3 ou mais novo, Apple silicon (arm64) ou Intel (x64), um instalador nativo para cada (não é universal). 13.3 é o piso defensável: o macOS 13.0 a 13.2 trazem Safari 16.1 a 16.3, sem `@property`. Hoje isso é só documentação: a declaração no instalador (`LSMinimumSystemVersion`) está no PR #167 e só vale depois dele; até lá o macOS não impede a abertura em uma versão mais antiga. <!-- proof: release.yml macos-15 / macos-15-intel; tauri.conf.json sem bundle.macOS.minimumSystemVersion (padrão do Tauri 10.13); https://v2.tauri.app/reference/config/ --> |
| Linux | x86_64 (64 bits), WebKitGTK 2.40 ou mais novo (`webkit2gtk-4.1`) e glibc 2.35 ou mais nova (Ubuntu 22.04+, Debian 12+, Fedora 36+, segundo o comentário do `release.yml`). O Ubuntu 22.04 sem atualizações traz o WebKitGTK 2.36, abaixo do piso; com as atualizações de segurança traz a 2.50.x. O `.deb` depende de `libwebkit2gtk-4.1-0` e, depois do PR #167, de `(>= 2.40)`; antes disso não exige versão. <!-- proof: release.yml build ubuntu-22.04, appimage+deb; https://launchpad.net/ubuntu/+source/webkit2gtk; https://v2.tauri.app/distribute/debian/ --> |

**Não verificado:** a Apple não afirma literalmente que o macOS 13.3 traz o Safari 16.4 (só fonte secundária); se o WKWebView de um app no macOS 12 ou anterior recebe um Safari 16.4 instalado à mão; o mínimo real (`minos`) dos binários empacotados do macOS, incluindo o sidecar em PyInstaller, que pode ser maior que 13.3; o que exatamente o macOS faz ao abrir um app abaixo do `LSMinimumSystemVersion`; que o WebKitGTK 2.40 equivale ao Safari 16.4 com `@property` ligado por padrão (a 2.40 é um piso plausível, não provado); se o AppImage leva o próprio WebKit (pelo código do empacotador do Tauri, sim; nosso arquivo não foi inspecionado); o efeito de `(>= 2.40)` no `.deb` gerado; a versão de WebKitGTK do Fedora 36 e de distros não listadas. Os instaladores não são assinados: veja abaixo e baixe só da página da tag, linkada no fim, nunca de `/releases/latest`.

## Instaladores sem assinatura

Nenhum instalador é assinado por um editor nem notarizado. O build assina uma plataforma só quando os segredos dela existem no ambiente `release`. <!-- release.yml signing steps; docs/ci-security.md#code-signing -->

| Plataforma | Arquivo | O que você verá |
| --- | --- | --- |
| Windows 10/11 x64 | `OHarness-windows-x64-setup.exe` | SmartScreen: "Windows protected your PC", editor desconhecido. Escolha *More info* e depois *Run anyway*. Precisa do WebView2 Runtime (presente no Windows 10/11 atual). |
| macOS Apple silicon | `OHarness-macos-arm64.dmg` | Só assinatura ad hoc, sem notarização. O Gatekeeper bloqueia a primeira abertura. *Ajustes do Sistema > Privacidade e Segurança > Open Anyway*, ou `xattr -dr com.apple.quarantine /Applications/OHarness.app` depois de verificar o arquivo. |
| macOS Intel | `OHarness-macos-x64.dmg` | Igual ao Apple silicon. |
| Linux x86_64 | `OHarness-linux-x86_64.AppImage`, `OHarness-linux-amd64.deb` | Sem aviso e sem assinatura embutida. Construído no Ubuntu 22.04: precisa de glibc 2.35 ou mais nova (Ubuntu 22.04+, Debian 12+). |

Verifique cada download antes de executá-lo, na pasta com os arquivos:

```bash
sha256sum --check --ignore-missing SHA256SUMS
gh attestation verify OHarness-windows-x64-setup.exe --repo klebertiko/oharness
```

No segundo comando, use o arquivo que você baixou. `OHarness-sbom.cdx.json` é o SBOM CycloneDX; todo instalador tem uma atestação de proveniência de build e uma de SBOM. As atestações provam onde um arquivo foi construído; elas não substituem a assinatura de um editor.

## Limitações conhecidas

- **Nenhum mínimo de WebView é imposto ainda.** Os requisitos acima são documentação: o instalador não checa a versão do WebView do sistema (as declarações para macOS e `.deb` estão no PR #167), e a renderização ainda varia entre WebView2, WKWebView e WebKitGTK. <!-- docs/adr/0001-desktop-packaging.md lines 67 and 111; no minimum in tauri.conf.json -->
- **Os desktops macOS e Linux foram construídos e tiveram o sidecar testado (smoke) na CI, mas a janela do app nunca foi aberta lá pelo pipeline do mantenedor.** O smoke do desktop (janela, health, saída limpa) roda só no Windows, e a sonda de WebView é de melhor esforço em runners hospedados. <!-- release.yml lines 174-250, 462-465; docs/ci-security.md#releases -->
- **Local dos dados:** a casca desktop inicia o sidecar com `OH_DATA_DIR` apontando para o diretório de dados local do app, nomeado pelo identificador do Tauri: `%LOCALAPPDATA%\dev.oharness.app` no Windows (banco `harness.db` e `secrets`), e a pasta equivalente por usuário no macOS e no Linux (esses caminhos não foram verificados aqui). `%LOCALAPPDATA%\OHarness` e `~/OHarness` valem só para um sidecar executado sozinho, sem `OH_DATA_DIR`. <!-- src-tauri/src/lib.rs spawn_sidecar (app_local_data_dir -> OH_DATA_DIR); backend/sidecar_entry.py _data_dir; src-tauri/tauri.conf.json identifier -->
- **Efeitos colaterais da renomeação (PR #144).** O identificador do Tauri mudou de `dev.openharness.app` para `dev.oharness.app`, então a pasta de dados local do app muda junto: uma instalação de um build anterior mantém `harness.db` e `secrets` em `%LOCALAPPDATA%\dev.openharness.app` (confirmado na máquina do mantenedor), enquanto o build novo usa `%LOCALAPPDATA%\dev.oharness.app`. Nada é movido automaticamente. O armazenamento em arquivo deriva a chave do caminho dos segredos, então chaves guardadas por um build anterior precisam ser digitadas de novo. O código de compatibilidade cobre só outros casos: entradas do chaveiro do SO sob o nome antigo de serviço `openharness` são lidas e migradas no primeiro acesso; com `OH_SECRETS_DIR` indefinido (execuções de desenvolvimento), `~/.openharness/secrets` continua em uso enquanto `~/.oharness/secrets` não existir; e `OPENHARNESS_BACKEND_URL` e `OPENHARNESS_CURSOR_WSL_*` ainda funcionam como alternativas às variáveis `OHARNESS_*`. Não houve release pública com o nome antigo. <!-- git show 4cdc868; backend/secret_store/{factory,keychain,file_store}.py; backend/sidecar_entry.py; src-tauri/tauri.conf.json -->
- O Cursor no Windows roda dentro do WSL2 (distro padrão `Ubuntu-24.04`). <!-- README.md Providers; PR #80 -->
- Modo Auto no Windows: nomes de dispositivo reservados (`CON`, `NUL`, ...) como operandos de `ls`/`git` não são recusados, segundo a issue #109 (aberta, não bloqueante); no pior caso um comando trava até o timeout. Um junction `.git` agora é detectado e pergunta em vez de aprovar automaticamente (#146).
- A transcrição do Studio com o Nilo vale só para a sessão e as respostas não chegam em streaming. <!-- README.md "Nilo in Studio" -->
- Licença de pré-visualização pública: código disponível para avaliação, termos de redistribuição ainda não definidos. <!-- README.md License -->
