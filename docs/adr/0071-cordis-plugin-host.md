# ADR 0071 — Host Node de Cordis plugins

Status: proposta desta sessão (2026-11-12), spike da issue #466 (parte de #441). 0068 está no PR #444 e 0069 no PR #467; este documento é o 0071. Revisto em 2026-11-19 pela #508 (isolamento do plugin) e pela #486 (limites do host).

## Contexto

A Camada B precisa de um host Node, separado do sidecar FastAPI, no estilo do DeepSeek Harness (DSH): escuta só em `127.0.0.1`, porta e token efêmeros, compatibilidade de servidor para ferramentas, comandos, eventos e serviços, confirmação humana na instalação, e os avisos de segurança do DSH.

O DSH vende Cordis `4.0.0-rc.11` no commit `0b96d9fd517b998e44e2209560c9e5f0671ce933`. O pacote publicado `@deepseek-ai/cordis` é outra linha (4.1.0 na data deste pin). O DSH não tem permissão por plugin, deixa o agente aprovar scripts de build e é software de prévia.

## Decisão

1. O host mora em `cordis-host/`. Não entra no processo do FastAPI e não muda a via de assinatura (`credential.kind=cli`).
2. O processo escuta só em `127.0.0.1` com porta `0`. O token tem 32 bytes, vai no header `Authorization: Bearer`, e a comparação é o hash SHA-256 dos dois lados. Token na query não autentica. O header `Host` tem de ser `127.0.0.1` e a porta deste processo. Uma variável de ambiente de porta não move o bind.
3. A cópia do Cordis é o tarball npm `cordis@4.0.0-rc.11` (integridade no `package-lock.json`; `gitHead` do registro igual ao commit do `vendor/README.md` do DSH). O specifier `@deepseek-ai/cordis` resolve para esse mesmo módulo, para um plugin do DSH e o host compartilharem uma instância. Não instalamos `@deepseek-ai/cordis@4.1.0`, e o tarball entra como publicado, sem modificação local.
4. Há dois runtimes. `isolated` é o padrão (omissão significa `isolated`): o plugin roda num processo Node próprio, descrito no item 10. `in-process` roda no processo do host com o alcance do usuário, e por isso o pacote só é aceito se declarar as quatro capacidades (`files`, `network`, `processes` e `credentials`); sem isso a prévia recusa com `runtime-not-supported`. Outro valor também é recusado. Omissão de `capabilities` não concede nada; antes, ela listava as quatro.
5. A instalação importa o módulo só depois de `accept: true` e de um digest que amarra a versão do aviso, o nome, a versão, o caminho real, o runtime, as capacidades e os scripts de lifecycle. O aviso (versão 3), em en e pt-BR, diz o que o processo isolado não alcança sem capacidade, o que cada capacidade concede (e que `files` alcança o código do próprio host), que a rede não é limitada e alcança os serviços do computador, inclusive este host, que `in-process` tem tudo de uma vez, e que sandbox e aprovação protegem as ações do agente e não o código do plugin além desses limites. Confirmar o digest é o que concede as capacidades declaradas.
6. Scripts `preinstall`, `install`, `postinstall` e `prepare` nunca são executados. O corpo `approvedBuilds` ou `allowBuilds` é recusado. Confirmar esses scripts é `scripts: "do-not-run"`.
7. O host oferece serviços de servidor: `tools` e `commands` como subconjuntos, eventos pelo `ctx.emit` do Cordis (nomes `internal/` recusados), e serviços Cordis. `sessionProjections` só guarda o registro; não dobra um log de sessão. Com o runtime `isolated`, do filho para o host só voltam **nomes**: de tools, de comandos, de projeções e de serviços. A instância de um serviço e os eventos que o plugin emite ficam no processo dele; não cruzam para o host nem para outro plugin. Um plugin isolado não consome o serviço de outro.
8. `defineTool` deste host não valida o schema dos argumentos. O pacote `@deepseek-ai/dsh-tools` não está instalado. Schemastery é o tarball npm `3.18.0` (`gitHead` `9e1f54f8`), não o commit `cf0b7e54` que o DSH vende. Patches de bundle (`dsh.bundle.patch`) são reconhecidos e não aplicados.

9. O pacote tem de estar, depois de resolver links, estritamente dentro de uma pasta de plugins que o app controla: `OH_CORDIS_PLUGINS_DIR` (caminho absoluto) ou, sem ela, `~/.oharness/plugins`. Só o processo pai escolhe essa pasta; a API HTTP não. Um link dentro do pacote é recusado.
10. O digest também amarra o arquivo de entrada (caminho relativo) e um sha256 de todos os arquivos do pacote (caminho e hash de cada um, em ordem). Na instalação, o host copia o pacote para uma pasta própria e privada a partir dos mesmos bytes que hasheia, recusa se o hash não é o confirmado, e roda a cópia: editar o original depois disso não muda o que roda. Um pacote já carregado só responde do cache se o hash dos arquivos for o mesmo; se mudou, a instalação é recusada com `confirmation-mismatch`.

    **Fronteira do runtime `isolated`.** Cada plugin roda num processo filho (`child_process.spawn` do `node`, com quatro pipes, stdin, stdout, stderr e fd 3, e sem canal IPC do Node) com o Permission Model do Node (`--permission`). Sem capacidade, esse processo:
    - só lê o snapshot do pacote e os módulos fixados do host (`src/`, `vendor/`, `node_modules/` e o `package.json` de `cordis-host/`), por `--allow-fs-read`. `test/` e `proofs/` ficam de fora;
    - não escreve em disco (sem `--allow-fs-write`);
    - não abre processo (sem `--allow-child-process`), nem worker, addon ou WASI (essas flags nunca são passadas);
    - não recebe as variáveis de ambiente que o host tem. No POSIX o ambiente do filho é vazio. No Windows o host passa só `SystemRoot`, que o Node exige para subir, e o libuv completa os padrões do usuário (HOMEPATH, USERNAME, USERPROFILE, TEMP, PATH e outras): o ambiente não fica vazio, mas nenhuma variável própria do host chega. `NODE_OPTIONS` nunca passa, porque poderia somar flags de permissão;
    - não escreve no stdout do host, onde vai o banner com o token: o stdout e o stderr dele vão, linha a linha, para o stderr do host, com o prefixo `[plugin <nome>]`, sem sequências de controle de terminal, sem caracteres de controle C0/C1, sem os controles bidi (U+061C, U+200E, U+200F, U+202A a U+202E, U+2066 a U+2069) que reordenam o que o terminal mostra e sem os separadores de linha e de parágrafo (U+2028, U+2029). Uma linha acima de 8 KiB chega cortada em pedaços de até 8 KiB;
    - não alcança o inspector do host. O Permission Model não cobre `process._debugProcess(pid)` (que abre o inspector de outro processo Node, por SIGUSR1 no POSIX e por thread remota no Windows) nem `process.kill`/`process._kill`, nem `os.setPriority`. O primeiro módulo do filho (`src/child-guard.ts`) troca os quatro, antes de qualquer código do plugin, por guardas não graváveis e não configuráveis. `_debugProcess` sempre recusa. `kill` e `_kill` só aceitam um pid que seja um inteiro primitivo na faixa int32 positiva (1 a 2^31−1), porque o Node trunca o pid para int32: 2^32 viraria 0, o grupo de processos, e host + 2^32 viraria o host. O sinal também tem de ser primitivo: `kill` aceita string ou inteiro, e `_kill`, que é a chamada crua, só inteiro. Os dois repassam ao Node o valor que checaram: um objeto com `valueOf` ou `toString` é recusado, porque o Node o converteria de novo depois da checagem e ele poderia responder outro pid. Sem `processes`, o plugin só sinaliza o próprio pid; com `processes`, qualquer pid dessa faixa menos o do host. `os.setPriority` só muda a prioridade do próprio processo (pid omitido, 0 ou o próprio), com ou sem `processes`; a troca vale para `import os`, `import { setPriority }` (o guard chama `syncBuiltinESMExports`), `require` e `process.getBuiltinModule`. `process.binding` já é recusado pelo Permission Model. O host roda com `--disable-sigusr1` (scripts `start` e `test`) e ignora SIGUSR1, o que cobre também um processo que o plugin abre com `processes`;
    - tem o heap limitado a 512 MiB (`--max-old-space-size=512`).

    Cada capacidade confirmada tira um limite: `files` passa `--allow-fs-read=*` e `--allow-fs-write=*`; `processes` passa `--allow-child-process`; `credentials` passa o ambiente do host. O hook de resolve continua dentro do filho e recusa o `import` que sai da cópia, dos built-ins e dos módulos fixados antes de o arquivo rodar.

    `files` equivale a controlar o host: com leitura e escrita em `*`, o plugin pode sobrescrever `cordis-host/src`, que o host e os outros plugins carregam no próximo arranque. `files` é o alcance total do usuário em disco, não uma pasta.

    **Canal.** Não há canal IPC do Node, que faz o parse da mensagem inteira antes de alguém medi-la. O host passa um pipe no fd 3 e o filho escreve nele NDJSON (uma mensagem JSON por linha); o host conta os bytes da linha **antes** do parse (`src/lines.ts`) e corta no teto de 1 MiB, então o teto é real. O filho avisa `ready`, recebe `load`, e devolve `loaded` com o estado do fiber e os nomes de tools, comandos, projeções e serviços. Depois, `invoke` e `command` voltam como `result`. `exec.agent.session.append` volta como `session-append`, e `emit` e `abort` vão para o filho. O host não confia no filho, que divide o processo com o código do plugin: toda linha é lida por um schema estrito (`src/ipc.ts`, zod). Uma linha acima do teto, malformada ou fora de ordem mata o processo e marca o plugin como `failed`. Um filho que morre falha as chamadas pendentes, e o host segue de pé. Um nome de tool ou comando que outro plugin já usa recusa a instalação.

    `session-append` só aceita os eventos da allowlist `SESSION_EVENTS` (hoje só `todo/write`), com até 64 KiB de dados por evento (bytes UTF-8 do JSON, não unidades UTF-16) e 100 eventos por chamada; fora disso, a chamada falha. Quando uma chamada passa do prazo (item 13), o host manda um `ping`: se o `pong` não volta em 2 s, o filho travado é morto e o plugin fica `failed`.

    `emit` vai, sem filtro, para todos os plugins isolados carregados, como o `ctx.emit` do Cordis faz no mesmo processo. Um plugin isolado recebe todo evento que a UI ou o sidecar emitem, mesmo os que ele não declarou ouvir. Filtrar por eventos declarados fica para quando o manifesto tiver esse campo.

    **Limites dessa fronteira**, com as docs do Node (`nodejs.org/docs/latest-v22.x/api/permissions.html`) como fonte:
    - O Node usado é o do `.nvmrc` e do CI, `22.20.0`, e o `engines` exige `>=22.20.0`. O sidecar sobe este host (ver "Empacotamento e supervisão"). No 22, o Permission Model é "Stability: 2 - Stable" desde a v22.13.0. `--allow-child-process`, `--allow-worker`, `--allow-addons` e `--allow-wasi` são "1.1 - Active development". Os testes rodam no 22.20 do CI e no 24 local.
    - **Rede não é limitada.** O Node 22 e o 24 não têm permissão de rede. `--allow-net` só aparece na v25.0.0, e ainda como "1.1". A capacidade `network` é declaração, e o aviso diz isso. Sem ela, o filho ainda alcança a internet e os serviços de loopback da máquina, inclusive este host (que exige o token do item 2, que o filho não recebe) e o sidecar. Quando o Node do host for 25 ou mais novo, `network` passa a ter flag própria.
    - O Node segue links simbólicos para fora das pastas liberadas. O snapshot recusa qualquer link (item 9), e por isso essa brecha não se aplica à cópia.
    - Um descriptor de arquivo herdado passa por fora do modelo. O filho recebe só pipes do host: stdin, stdout, stderr e o canal no fd 3.
    - `node:sqlite` não é coberto pelo modelo para arquivos. O plugin que o usar pode ler bancos SQLite que o usuário alcança.
    - `processes` é o alcance do usuário: um programa iniciado pelo plugin roda fora do modelo, e o aviso diz isso.
    - `in-process` não tem fronteira nenhuma; só o hook de resolve evita acidentes. Ele existe para código nosso ou vendorizado que precisa dividir a instância Cordis com o host, como a prova 2.
    - Não há limite de CPU por plugin, e o de memória é só o heap do V8 (buffers fora do heap não contam). Um laço infinito trava só o filho: o host responde por prazo (item 13) e mata o filho que não responde ao ping.

    Por isso o PR e o aviso falam em processo separado com limites de arquivo, de processo e de ambiente, e não em isolamento completo: a rede, a CPU e os serviços de loopback continuam ao alcance do plugin.
11. O token fica só com a UI e o sidecar, nunca com o agente. Quem tem o token consegue fazer prévia e instalação sozinho (o digest volta na resposta 409), então entregar o token ao agente equivale a deixar o agente instalar código.
12. O pai segura o stdin do host. Quando o stdin fecha, inclusive porque o pai morreu sem mandar sinal, o host para de escutar e sai. Subir o host com stdin em `/dev/null` faz ele sair na hora. Se o `close` não termina em 5 s (um `dispose` que nunca acaba), o host mata os filhos, apaga os snapshots de forma síncrona e sai com 1, para nada sobrar na pasta temporária (`src/shutdown.ts`). O prazo segura o event loop de propósito: um `dispose` preso numa promise que não segura handle nenhum deixaria o loop esvaziar e o host sair com 0 sem limpar. `test/lifecycle.test.ts` sobe o host real com um plugin assim e exige saída 1 em cerca de 5 s e o snapshot apagado. O filho roda fora da pasta do snapshot, porque no Windows um processo com o cwd lá impede apagá-la. Um SIGKILL no host (ou encerrar o processo pelo Gerenciador de Tarefas no Windows) não passa por nada disso: os snapshots `oharness-cordis-snap-*` ficam órfãos na pasta temporária.
13. `tools/invoke` e `commands/execute` têm prazo (30 s por padrão): depois dele a resposta é de erro e o sinal aborta. No máximo 16 chamadas rodam ao mesmo tempo; a 17ª recebe 429 `busy`. O servidor aceita até 64 conexões. O abort por desconexão escuta o `close` da resposta e só dispara se ela não terminou. O listener de `connection` é registrado antes do `listen`. A `message` de erro de um plugin volta em `/v1/plugins` só para quem tem o token, que é a UI ou o sidecar (item 11): isso fica aceito, sem redação.

## Empacotamento e supervisão (#523)

**Empacotamento.** O instalador leva o Node 22.20.0 oficial, e não exige Node no sistema nem compila as fontes para JS. `scripts/build-cordis-host.mjs` baixa o arquivo de nodejs.org por https e só o aceita se o SHA256 for o fixado no script (copiado do `SHASUMS256.txt` da versão; cobre win-x64, linux-x64, darwin-x64 e darwin-arm64, e qualquer outra plataforma é recusada). Em seguida copia `src/`, `vendor/`, `package.json` e `package-lock.json` de `cordis-host/` e roda `npm ci --omit=dev --ignore-scripts`, tudo em `src-tauri/resources/cordis-host/` (fora do git), que o `tauri.conf.json` inclui como recurso. O `npm run tauri:build` e o `release.yml` chamam o script antes do `tauri build`. A shell passa `OH_CORDIS_NODE` e `OH_CORDIS_HOST_DIR` ao sidecar quando esse recurso existe. Em desenvolvimento o sidecar usa o `node` do PATH (22.20 ou mais novo) e o `cordis-host/` do repositório. O `.nvmrc`, o `engines` do host e o Node embutido têm de ser a mesma versão; um teste confere.

**Supervisão.** O sidecar FastAPI é o pai do host (`backend/cordis/supervisor.py`) e segura o stdin dele, o que fecha a cadeia do item 12: app, sidecar, host, processos dos plugins. Matar qualquer elo fecha o pipe e o de baixo sai; parar o sidecar pelo `lifespan` fecha o stdin do host, espera 6 s e só então mata a árvore. O host sobe numa thread e a falta de Node, do `cordis-host/` ou das dependências deixa o estado em `unavailable` com o motivo, sem derrubar o sidecar. `OH_CORDIS_NODE` só vale como caminho absoluto de um arquivo. O banner traz `node` (o `process.version` do host): abaixo de 22.20, o sidecar encerra o host e fica em `unavailable` com "Node.js 22.20.0 or newer is required.", sem reiniciar; o Node nunca é chamado à parte só para dar a versão. Um Node velho demais para as flags do host (sai com `bad option` antes do banner) recebe a mesma mensagem, também sem reinício. Não achar ou não poder executar o Node (`FileNotFoundError`, `PermissionError`) também é definitivo; outro erro de sistema na criação do processo (muitos arquivos abertos, falta de memória) entra no reinício com espera. `start()` de novo tenta outra vez. O banner (porta e token) é lido do stdout e fica só na memória do sidecar; nenhuma rota o devolve e as linhas de log que o citem são redigidas. Um host que sai depois de pronto é reiniciado com espera crescente, no máximo 3 vezes em 60 s, e depois fica em `failed`. O stderr do host vai para dois buffers circulares: um por plugin (pelo prefixo `[plugin <nome>]` do item 10) e um do host. `OH_CORDIS_DISABLE=1` desliga tudo.

**Registro.** `<data_dir>/cordis-plugins.json` guarda, por plugin, nome, versão, fonte, pasta, o digest confirmado, os scripts que não rodam, as capacidades confirmadas e `enabled`. Quando o host sobe, o sidecar reinstala os `enabled` com o digest guardado, sem nova confirmação. Se os bytes mudaram, o host recusa (`confirmation-mismatch`) e o item fica `changed`, pedindo confirmação nova.

**Fontes** (`backend/cordis/sources.py`). npm: nome e versão exata, metadados em `registry.npmjs.org`, tarball do mesmo host, `dist.integrity` sha512 conferida (sem ela, ou diferente, recusa). GitHub: `owner/repo` e commit de 40 hex (branch e tag são recusados), baixado de `codeload.github.com`, com subpasta opcional. Local: cópia de uma pasta absoluta; qualquer link ou junção recusa, e `node_modules` e `.git` não entram. Tarball: URL https de um `.tgz` com sha512 ou sha256 obrigatório (SRI ou hex), baixada com as mesmas checagens do índice do Descobrir (todo IP resolvido global, conexão no IP checado, sem redirect, timeout de 30 s, teto de 20 MiB), ou `.tgz` local por caminho absoluto (UNC e link recusados; hash informado é conferido). Toda fonte passa pela mesma extração. A extração é manual: só arquivos e pastas regulares, nomes que ficam dentro do destino, no máximo 2000 arquivos e 20 MiB, e nada é escrito antes de todo o arquivo ser verificado. Nenhum script roda e nenhuma dependência é instalada; dependências fora de `cordis`, `@deepseek-ai/cordis` e `schemastery` viram o aviso `unmet-dependencies` na prévia.

**Rotas.** O sidecar expõe `/cordis/*`. Ler `status` e `plugins` vale com o token do sidecar. Ver logs e exportar, buscar, instalar, ligar, desligar e remover exigem a credencial humana, como `/factory/secrets` (403 `human_only`). Instalar só carrega depois de `accept: true` e do digest da prévia (item 5).

**Log ao vivo e Cancelar.** `POST /cordis/plugins/fetch {live: true}` responde na hora com o id; `GET /cordis/plugins/fetch/{id}` devolve os passos (`downloading`, `copying`, `verifying`, `extracting`, `preview-ready`, `installing`, `done`, `failed`, `cancelled`) e `DELETE` (só humano) liga o evento de cancelamento, que o download confere entre pedaços de 64 KiB, espera a thread e apaga a pasta de staging. O mesmo `DELETE` descarta uma prévia pronta ("Não instalar").

**Scripts por pacote.** Para cada script de lifecycle da prévia a pessoa escolhe "Aceitar sem executar" ou "Não instalar". `install` exige `scripts_accepted` igual aos scripts daquela prévia e o digest dela; a decisão não é guardada para outro pacote nem outro digest. O host continua recebendo `scripts: "do-not-run"`: nenhum script roda.

**Exportar.** `GET /cordis/plugins/{id}/export` gera um `.tgz` reproduzível (nomes ordenados, sem data, dono nem modo da máquina, gzip sem data) e `GET /cordis/plugins/{id}/export/index` um índice `format: 1` com o plugin, montado só do `package.json` e dos arquivos: fonte npm, git com commit, ou tarball com o sha512 do `.tgz` exportado (para pasta local, `url` relativo que a pessoa troca pelo endereço https). Nada é publicado; a tela diz "Exportar".

**Capacidades na tela.** A prévia e o detalhe mostram sempre as quatro: `isolated` sem a capacidade mostra "bloqueada" (o processo não alcança); declarada e confirmada, "aceita" com o que concede; `network`, "só declarada: a rede não é limitada"; `in-process`, "sem limites".

**Descarregar.** `POST /v1/plugins/unload {name}` no host: o plugin isolado tem o processo parado, o `in-process` tem o fiber descartado, a entrada sai do mapa e a cópia privada é apagada. Assim outra versão se instala sem reiniciar o host, e é o que o sidecar faz ao trocar de versão, desligar ou remover.

**Não coberto.** O recurso do instalador e a resolução do `resource_dir` no Windows não foram exercitados num `tauri build` completo nesta fatia. O job `cordis host` e o pytest rodam em Linux; o Windows só roda o subconjunto do item "O que o CI não cobre no Windows".

## Modo criador, Descobrir e rotas de proxy

**Modo criador: o agente nunca instala.** O modo é da thread de chat. A pessoa o liga para a conversa atual (`POST /cordis/creator {thread_id, enabled}`, só humano; fica em `<data_dir>/cordis-creator.json`, no máximo 200 threads), sem enviar mensagem e sem mexer no rascunho; o composer mostra "Modo criador", que se desliga com um clique. O pedido `/execute/direct` manda `creator_thread_id`, e o `ToolBroker` só oferece `cordis_plugins` (e a skill `backend/cordis/skill/SKILL.md` no prompt de sistema) se o sidecar tem o modo ligado para essa thread e as `tools` do pedido são da mesma thread. Assim o modelo não liga o modo sozinho. Nesse caso `/execute/direct` cria o broker mesmo quando o pedido não traz `tools`. As ações são `list`, `scaffold {name, kind: tool|command|service}`, `write_file`, `read_file`, `preview`, `request_install`, `logs`, `api_catalog` (serviços, tools e comandos do host vivo por `GET /v1/services` e `/v1/plugins`, só nomes, sem código) e `starters` (os arquivos de partida). O cartão de aprovação do chat descreve a ação ("Escrever arquivo do plugin x", "Pedir instalação de x"):
- todas passam pelo `tool_approval` das outras ferramentas, uma aprovação por ação;
- o modo Plan recusa a ferramenta;
- argumento que nunca seria válido falha antes de pedir aprovação;
- o resultado traz `status` (`applied`, `pending-approval`, `failed`) e `nextStep`.

A ferramenta só escreve em `<plugins>/dev/<nome>`. O caminho é relativo, com `/`, sem parte vazia, `.`, `..`, oculta, drive ou `:`, e não passa por link nem junção. Cada arquivo tem até 256 KiB, e o pacote até 200 arquivos e 2 MiB. O `scaffold` sai `isolated` e sem capacidades.

`request_install` copia o pacote pela fonte local, faz a prévia no host e deixa um pedido pendente com o digest dos arquivos de dev. Só `POST /cordis/requests/{id}/approve`, com a credencial humana, instala, com o digest da prévia que a pessoa viu. Se os arquivos mudaram depois do pedido, ele fica `stale` e é recusado (409). Um pacote mudado depois de instalado precisa de pedido novo; a cópia instalada não muda. `logs` só lê plugins que vieram da área de dev. O token do host continua só no sidecar (item 11).

**Descobrir.** A pessoa informa a URL https de um índice estático `format: 1`, e o sidecar o busca por `POST /cordis/index/fetch` (só humano):
- o host da URL é normalizado e resolvido, e qualquer endereço que não seja global recusa;
- a conexão vai ao IP checado, com SNI e Host do nome, o que fecha o rebinding de DNS, e redirect é recusado;
- timeout de 10 s e teto de 512 KiB;
- só passam texto limpo (sem controles C0/C1 nem bidi, com teto por campo) e fontes instaláveis: npm com versão exata, GitHub com commit de 40 hex ou tarball https com hash;
- a tela mostra o texto sem HTML, sob o aviso fixo no topo, nunca recolhível, "Lista não revisada: os índices são de terceiros; confira a fonte antes de instalar";
- "Inspecionar" leva à mesma prévia e à mesma confirmação do fluxo de adicionar.

**Rotas de proxy.** `POST /cordis/tools/invoke {name, args}` e `POST /cordis/commands/execute {line}` repassam ao host com o token do sidecar. São o caminho do agente até as tools e os comandos dos plugins, sem receber o token do host. `POST /cordis/plugins/install` aceita `config` (JSON até 16 KiB), guardado no registro e repassado ao `apply(ctx, config)`; o `tool-todo` do DSH exige um.

**Compatibilidade.** `backend/tests/test_cordis_compat.py` copia três pacotes de `cordis-host/` para uma pasta, instala pela fonte local nas rotas `/cordis/*`, com o host real, e exercita cada um:
- o nosso (`proofs/our-plugin`): tool, comando e evento pelas rotas de proxy;
- o `directory-picker` do DSH: a prévia mostra `in-process` e as quatro capacidades;
- o `tool-todo` do DSH: isolado no serviço `tools`, e a regra de sessão do próprio plugin recusa a chamada sem agente.

## Consequências

As três provas desta fatia estão em `cordis-host/test/proofs.test.ts`: a prova 1 roda isolada (pid diferente do host), a prova 2 roda `in-process`, e a prova 3 roda o `tool-todo` do DSH isolado, com `session.append` atravessando o canal do fd 3. As recusas do item 10 estão em `cordis-host/test/isolation.test.ts`, uma por limite (inclusive a prova direta de que o Permission Model está ligado no filho: `process.permission.has('fs.write')` é `false`), as do canal em `test/channel.test.ts` e a do inspector em `test/lifecycle.test.ts`. Rodam no job `cordis host` do CI, em Linux.

**O que o CI não cobre no Windows.** Não há job Windows do `cordis host`. A linha de `setup-safe-chain` desse job precisaria de um `nosemgrep`, e isso fica para decisão de quem mantém o repo. Assim, só rodam localmente, no Windows de quem desenvolve:
- a recusa de import com a caixa das letras trocada (`test/limits.test.ts`, teste "on Windows, a host file named with other letter case is still refused", que faz `skip` fora do Windows);
- `process._debugProcess` por thread remota. No Linux ele vira SIGUSR1, que o CI cobre; o ramo do Windows não é exercitado;
- o ambiente do filho completado pelo libuv (HOMEPATH, USERPROFILE, TEMP, PATH e outras). O teste de `credentials` só prova a ausência de uma variável própria do host;
- `--disable-sigusr1` num sistema sem SIGUSR1. O teste do inspector no Windows só chama `_debugProcess`, e o teste de SIGTERM faz `skip` lá.

O que os testes desta fatia não fecham, em nenhum sistema: um pipeline de ferramentas em volta do host (este host não tem um), o log de sessão, a dobra de projeções, modificações sobre o Cordis fixado (este host não faz nenhuma), patches de bundle (reconhecidos e ignorados) e a rede no runtime isolado. A tela "Cordis Plugins" e o modo criador estão na seção anterior.

## Alternativas rejeitadas

- Depender de `@deepseek-ai/cordis`: traz a linha republicada, não o rc.11 que o DSH registra.
- Modificar o Cordis fixado: quebraria o pin auditável.
- Deixar o agente aprovar scripts de instalação: é a fraqueza que esta fatia não repete.
- Afirmar que capacidades isolam o plugin sem fronteira por trás: o aviso do DSH diz o contrário. Agora `files`, `processes` e `credentials` têm uma fronteira de processo; `network` continua só declarada, e o aviso diz isso.
- Bloquear `node:module`, `fs` ou `child_process` por hook no mesmo processo: `createRequire`, `process.binding` e o próprio `process` contornam, e isso daria uma falsa sensação de sandbox.
- Worker threads com `--permission`: o modelo do Node não herda para worker threads ("The model does not inherit to a worker thread").
- Isolamento de SO (job object, seccomp, contêiner), como o da #420 para as tools do broker: cobriria a rede, mas exige um mecanismo por sistema operacional. O processo filho com `--permission` funciona igual nos três e não fecha essa porta.
